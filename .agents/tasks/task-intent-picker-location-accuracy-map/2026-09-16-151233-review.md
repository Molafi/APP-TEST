# First-launch purpose picker, accurate location, and OSM map picker (review v1)

The change wires together the three user requests: a one-time "what do you want the app for" picker shown at first launch, a bump in device-location accuracy, and an OpenStreetMap-based pin picker so a location can be pointed at on a map. The purpose picker reuses the existing `SurveyPurpose` enum instead of inventing a parallel intent type, persists the choice under a new pref key, and uses a nullable provider state so "not chosen yet" is distinct from a deliberately-chosen `general`. Location accuracy goes from `low` to `high` with a 15s time limit, and the new map picker uses key-free OSM raster tiles (`flutter_map` + `latlong2`) so it works on Android, iOS and web without an API key. The confirm flow is extracted into `LocationController.selectPinnedLocation` so the reverse-geocode-then-apply path (and its null fallback) is testable without a map widget.

Watch for: the purpose-screen confirm sets provider state (which flips the router to Home) before it sets the target tab, so the first Home frame can briefly show the default Chat tab before correcting (possible); the map picker surfaces `geocodeFailed` ("Couldn't determine your city") for tile-server load failures, a message/cause mismatch (confirmed); two new dependencies are added and cannot be resolved in-sandbox (informational).

**Verdict**: APPROVED

## High-level view

The router branches on `appPurposeProvider` only after auth resolves, and the provider's nullable state is the single source of truth for whether the picker has been shown — `null` means "not chosen", any stored value (including `general`) means "chosen". This deliberately distinguishes an explicit `general` pick from a first launch, which is the right call and is directly tested.

The purpose choice fans out to three places: the persisted pref, the initial Home tab (via the pure `homeTabForPurpose` mapping), and the GeoResearch survey seed. The confirm handler applies these in an order that can produce a one-frame tab flash, because the state write that navigates happens before the tab is set.

Location accuracy is a two-line change (`high` + 15s `timeLimit`); the timeout it can now raise is already funneled through the existing catch in `useMyLocation` and lands as a generic error status.

The map picker is a self-contained bottom sheet over `flutter_map` with visible OSM attribution and a tile-error guard that degrades gracefully on web. Its confirm path delegates to `selectPinnedLocation`, which reverse-geocodes and falls back to the raw pinned coordinates with a localized label when the geocoder yields nothing. The only rough edge is that the tile-load error reuses a geocoding-failure string.

### Purpose fan-out ordering on confirm

```
_confirm():
  await setPurpose(chosen)   // sets state=chosen synchronously, THEN awaits prefs write
        │                    // router is watching appPurposeProvider -> rebuilds to HomeScreen
        ▼
  homeTabProvider = homeTabForPurpose(chosen)   // runs only after the await
  soilResearchController.setPurpose(chosen)
```

`setPurpose` assigns `state = purpose` before awaiting the SharedPreferences write, so the router sees a non-null purpose and schedules a rebuild to `HomeScreen` while `_confirm` is still suspended on the await. `homeTabProvider` is only updated afterward. Since `homeTabProvider` defaults to `HomeTab.chat`, Home can build on the default tab for a frame before the correct tab lands and the `IndexedStack` switches. It self-corrects (the providers live in the same container across the rebuild), so this is a visual flicker rather than a wrong-destination bug, and the same ordering exists in the settings re-choose handler. Setting the tab and seeding the survey before the awaited write — or ordering the tab assignment first — removes the flash. Confidence: possible (depends on frame timing; not reproduced against a running toolchain).

### Location accuracy and the new timeout path

The `timeLimit` makes `getCurrentPosition` capable of raising a timeout that the previous `low`/no-limit call would not; `useMyLocation` already wraps the call in a try/catch and routes unrecognised kinds to `LocationStatus.error`, so a timeout degrades to a generic error state rather than hanging. There is no dedicated timeout status, so the user sees a generic error message (not a "still searching / try again" hint) on a slow fix.

### Map picker: web degradation and reverse-geocode fallback

`NominatimService.reverse` swallows its own exceptions and returns `null`, so the offline/rate-limited/over-water cases all land on `selectPinnedLocation`'s fallback (a manual `PlantLocation` keeping the pinned coordinates with a localized `mapDroppedPin` label) rather than propagating out of the un-try/caught confirm handler. The `errorTileCallback` guard flips `_tileError` so a CORS-blocked or unreachable tile server surfaces a banner instead of crashing the sheet on web.

The tile-error banner reuses `l10n.geocodeFailed` — "Couldn't determine your city. Try searching manually." That message describes a geocoding failure, but the banner fires on tile *rendering* failures (network/CORS), so the shown text misdescribes the cause and points the user at manual search rather than a connectivity/web-support hint. A dedicated string would be clearer. Confidence: confirmed (the `errorTileCallback` sets `_tileError`, and the guarded banner renders `l10n.geocodeFailed`).

### New dependencies

`flutter_map ^7.0.2` and `latlong2 ^0.9.1` are added (key-free, web-capable, OSM raster tiles need only the already-present INTERNET permission, so no `setup_platforms.{sh,ps1}` change is expected). Both cannot be resolved or compiled in-sandbox (INTEGRATIONS_ONLY, no Dart SDK); dependency resolution, `MapOptions`/`errorTileCallback` API compatibility against flutter_map 7.x, and a web-preview smoke check all need a run on the user's toolchain. Informational, not a defect.

### Test coverage

The new tests exercise real code paths rather than static values. `map_picker_flow_test` drives `selectPinnedLocation` through both the successful reverse-geocode branch (asserts the geocoded city/country and preserved coordinates) and the null-fallback branch (asserts the `fallbackCity` label, preserved coordinates, and `isManual`), so reverting the fallback would fail it. `app_purpose_provider_test` covers not-chosen (`null`), persistence, restore-from-prefs, the deliberate-`general`-vs-not-chosen distinction, and unknown-value degradation — the distinction test would fail if the nullable-state design were collapsed. `purpose_screen_test` taps "Building" → "Continue" and asserts all three fan-out effects (purpose, tab, survey seed). `home_tab_for_purpose_test` is exhaustive over the enum.

Not tested: the confirm-ordering frame timing (no test asserts the first Home frame's tab, so the flicker would not be caught); the tile-error banner rendering and its message; the map widget itself (deliberately, since the flow was extracted to a provider for testability).
